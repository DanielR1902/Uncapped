# llm/ — Scoped Guardrails

See root `CLAUDE.md` and `spec.md` §6 before editing here.

## Responsibility
All OpenRouter interaction: request construction, structured-output parsing/validation, prompt templates, and response caching. This package interprets and contextualizes deterministic results from `engine/` — it never computes or overrides compatibility/pass-fail verdicts itself.

## Files
- `client.py` — `httpx`-based OpenRouter wrapper. Reads `OPENROUTER_API_KEY` and `OPENROUTER_MODEL` from env; no hardcoded model string committed to source. 15s timeout. Request headers include `HTTP-Referer`/`X-Title` alongside `Authorization`/`Content-Type` (harmless, standard OpenRouter attribution headers — not required for the API to function, confirmed by direct testing against the live endpoint). A non-2xx/429 response prints its `response.text` to stderr before raising `LLMUnavailableError`, so a real failure's exact cause is visible immediately rather than only "HTTP 404" with no body. `analyze_build(...)` is the only function `ui/` calls, and it **never raises** for an expected failure (missing key, timeout, connection error, non-2xx/429, schema-validation failure) — those all funnel through the internal `LLMUnavailableError` and come back out as a heuristic `BuildAnalysisResponse` (`source="heuristic"`) instead.
- `prompts.py` — the combined system prompt (synergy + bottleneck + insights in one call, per `spec.md` §6.3) and `build_request(...)`, which assembles `BuildAnalysisRequest` from a build state using `engine.compatibility`/`engine.scoring` pre-check results.
- `schemas.py` — `pydantic` models `BuildAnalysisRequest` and `BuildAnalysisResponse` (nesting `SynergyEvaluation`, `BottleneckAnalysis`, `ArchitecturalInsights`) matching `spec.md` §6.2/§6.4 exactly. All response parsing goes through these models; a validation failure is treated the same as an API failure (fallback, not a crash).
- `cache.py` — cache-key computation (`sha256` of `prompt_type|workload_profile|sorted(component_ids)`) and read/write against the `llm_cache` table via `db.repositories.llm_cache_repo`. Only a successful LLM response is cached — a heuristic fallback is recomputed fresh each call, never persisted, so it can't permanently shadow a later real call.
- `concierge.py` — a third, independent OpenRouter-backed feature: `get_concierge_response(user_message, conversation_history, catalog_summary, community_summary, current_build_context=None, advisory_context=None, drafts_summary=None, previous_builds_summary=None, current_page=None, viewed_post_id=None, active_currency="USD", currency_rates=None) -> dict` is a conversational assistant answering catalog questions, recommending shared community builds, assembling a whole new build from scratch (`load_build`), patching the user's ALREADY-ACTIVE build with an incremental request like "add a network card" (`modify_build` — needs `current_build_context`, a caller-assembled snapshot of the active `build_draft` including its `budget_ceiling`), handling a pure page-navigation request (`navigate`, `navigate_to` constrained to this app's 5 real page keys by the schema's own `Literal` type, including `"drafts"` — optionally also carrying a `filters` payload for a `"community"` destination, staged by `ui/` into a one-shot key for `ui/views/community.py` to resolve against live feed data, and an optional `reset_mode: bool` meaningful only with `navigate_to == "create_build"`; `navigate` performs NO database write of any kind when leaving `create_build` — `ui.state.teardown_builder()` (spec.md §7.9) only resets session state; the "Save as draft" checkbox in `ui/views/create_build.py`'s manual Save UI is the single explicit way to create a draft), deep-linking straight to one specific, already-shared community post's thread view (`open_community_build` — `post_id` resolved by the model against `community_summary`'s real `post_id` values, never a `build_id`, since the two are different ids on different rows; see `llm.schemas.ConciergeOpenCommunityBuildAction`'s docstring for why), synthesizing a concise (1-2 sentence) optimization/analysis answer from a caller-pre-fetched `advisory_context` (a `get_build_advisory` result — this module cannot call `llm.advisory`/compute one itself, since that needs a real `BuildState` of ORM rows requiring database access this module doesn't have), or driving a short "save my build (name + destination, with a FAST-TRACK shortcut firing immediately when the user's own first message already supplies both), then optionally publish it" flow (`save_build` — persist components to the real `draft_builds` table (`destination: "draft"`) or the real `builds` table (`destination: "build"`), under the user's own literal `name`; NOT zero-click by default, unlike `load_build`/`modify_build`/`navigate`, UNLESS the fast-track path fires; `publish_immediately`/`author_notes` — both optional, defaulting `false`/`null` — apply a publish in the SAME turn as the save, only when the SAME message also explicitly asked to publish; `source`/`source_post_id` — also optional, defaulting `"studio"`/`null` — pick WHICH build's data gets persisted: `"studio"` reads `current_build_context`/`build_draft` as above; `"community"` instead reads an ALREADY-shared `CommunityPost`'s own `Build` row (`source_post_id`, resolved via `current_page`/`viewed_post_id`/`community_summary` the same way `load_saved_build`'s own community source is, and zero-hallucination-guarded identically) — for a request to save/clone a build the user is VIEWING on the Community page directly, without first loading it into the Studio; `publish_build` — share a `"build"`-destination save from a PRIOR turn, once the user confirms "yes" to a publish follow-up and settles an optional description question; a `"draft"`-destination save has no publish path and never leads here), or loading an EXISTING draft/saved-build/community-build directly into the Build Studio for editing (`load_saved_build` — `source`/`id` resolved against `drafts_summary`/`previous_builds_summary`/`community_summary` respectively, distinct from `load_build`'s brand-new-build and `open_community_build`'s read-only thread view), or answering a bare "what's my current total?" question (a 10th intent, `action: null` always) by quoting `current_build_context["formatted_total"]` verbatim — see CURRENCY AWARENESS below for why. `name`/`destination` are both REQUIRED fields on `ConciergeSaveBuildAction` (no defaults) so Pydantic itself rejects a `save_build` action returned before the model has genuinely gathered both from the user. The save/publish multi-turn flow is resolved the exact same way the pre-existing budget guardrail resolves its own yes/no follow-up: purely by the model reading its own immediately-prior turn out of `conversation_history`, never via new session-state confirmation machinery in Python — the ONE genuinely new piece of caller-tracked state is WHICH real build id a `"build"`-destination `save_build` action produced, since the LLM has no way to know that (see `ui/CLAUDE.md`'s `concierge_last_saved_build` key). Follows `client.py`'s/`advisory.py`'s exact never-raises/`source`-tagged, single-shot pattern (its own internal `ConciergeUnavailableError`) — ONE system prompt + ONE payload + ONE `/chat/completions` call, deliberately not genuine multi-turn tool-calling (this project has never used OpenRouter's function-calling API and doesn't need it here). CURRENCY AWARENESS (spec.md §7.10): the model NEVER performs currency-conversion arithmetic itself — the same distrust the NO AGGREGATE TOTALS RULE already applies to summation, extended to conversion math. `active_currency` (`"USD"`/`"EUR"`/`"NIS"`, the real `st.session_state["selected_currency"]`) tells it which currency is active, but every price it may quote comes pre-converted/pre-formatted: `catalog_summary` entries' `display_price`, `community_summary` entries' `display_total_cost`, and `current_build_context`'s own `formatted_total`/per-component `display_price` — the model quotes these verbatim, never the raw `price_usd`/`total_cost` fields (which stay real, unconverted USD for the budget guardrail's own arithmetic and any zero-hallucination cross-check to reason over). `currency_rates` (e.g. `{"USD": 1.0, "EUR": 0.92, "NIS": 3.70}`, `ui.format.CURRENCY_RATES`) is the ONE narrow, deliberate exception to "never do currency math": intent 3's BUDGET CURRENCY CONVERSION rule lets the model divide a budget FIGURE STATED IN THE USER'S OWN MESSAGE (e.g. "build me a PC for 7000 NIS") by the matching rate to get a working USD budget for part selection — a single division, not the many-line-item summation the NO AGGREGATE TOTALS RULE distrusts it with, and it's never used to convert a price being quoted back (that always comes from `display_price`/`display_total_cost`/`formatted_total` instead). `ui/format.py::convert_to_usd` is the canonical Python definition of that same division, kept in sync with the prompt's own arithmetic instruction. `currency_switch` (`"USD"`/`"EUR"`/`"NIS"`/`None`, a TOP-LEVEL `ConciergeResponse` field — a sibling of `action`, not nested inside it, so it can co-occur with ANY action type or `None`) is set whenever the user's message explicitly names a currency, whether attached to a budget ("build me a PC for 10000 NIS") or standalone ("switch to NIS"). This module never touches `st.session_state` itself; `ui/components/chat_assistant.py` applies the actual switch (staged one-shot, since the currency selectbox already rendered earlier in the same script pass — writing its key directly here would raise `StreamlitWidgetAlreadyInstantiatedError`) and recomputes any authoritative total AFTER the switch, so a request naming a currency actually changes `active_currency` for every future turn, not just that one reply's wording — a real, confirmed gap BUDGET CURRENCY CONVERSION alone left open (it only ever affected which currency a REPLY described a build in, never `st.session_state["selected_currency"]` itself).

`catalog_summary`/`community_summary`/`current_build_context`/`advisory_context`/`drafts_summary`/`previous_builds_summary` are all pre-fetched/assembled by the CALLER (`ui/`) and passed in as plain arguments — this module never queries `db.repositories` or `engine/` itself, and never runs compatibility checks, real slot/budget quantity clamps, or the actual `create_build`/`set_public`/`create_post` database writes for `save_build`/`publish_build` (that's the caller's job after this returns, via `engine.compatibility`/`ui.state.resolve_effective_quantity_limit`/`db.repositories.builds_repo`/`db.repositories.community_repo`). Zero-hallucination enforcement is authoritative in Python: `_validate_action` re-checks every `(category, id)` pair in a `load_build`/`modify_build` action's `components` against the real `catalog_summary` given, every `modify_build.quantities` key against the `"RAM"`/`"Storage"`-only constraint, an `open_community_build` action's `post_id` against the real `"post_id"` values in `community_summary` given, a `load_saved_build` action's `id` against whichever of `drafts_summary`/`previous_builds_summary`/`community_summary` matches its `source`, and — the one exception to "`save_build`/`publish_build` are pure pass-throughs" — a `save_build` action whose `source == "community"` has its `source_post_id` cross-checked against `community_summary` the exact same way, raising `ConciergeUnavailableError` (-> heuristic) on any mismatch, exactly like `advisory.py::_validate_advisory_actions`. An ordinary `source == "studio"` `save_build`, and `publish_build`, still have nothing new to cross-check (neither carries an LLM-supplied catalog id or category in that case), so `_validate_action` treats them like `navigate` — a pure pass-through. `fix_warnings`/`optimize_bottleneck` (spec.md §6.7 intents 11/12) get the same pure-pass-through treatment for the same reason — neither carries any LLM-asserted catalog id, category, or post id at all: `fix_warnings`'s actual fix comes from `engine.solvers.resolve_compatibility_issues` and `optimize_bottleneck`'s rebalancing swap comes from `llm.advisory.get_build_advisory`'s own already-validated `within_budget.swaps`, both applied by `ui/components/chat_assistant.py` after this module merely recognizes the intent — root `CLAUDE.md`'s "compatibility is never LLM-gated" rule applies here exactly as it does to every other build-mutating action. A genuinely unexpected (non-anticipated) exception gets its full traceback logged to stderr before the same heuristic fallback, so a real bug is never silently invisible. The system prompt enforces a hard "exactly 1-2 short sentences, no hardware-history/build-philosophy tangents" STRICT BREVITY RULE (with explicit BAD/GOOD examples, and an explicit note that it scopes to the `reply` field only — a real regression showed the model sometimes over-applying it to an action's `explanation` field too, omitting it and failing validation; `explanation` is now optional/`= ""` on every action type as the authoritative fix, since it has no functional consumer in `ui/` anyway), an advisory-synthesis rule (never dump raw `pros`/`cons`/`within_budget`/`stretch_budget`), a budget-guardrail reply template (ask before returning an over-ceiling `load_build`/`modify_build`, confirmed via `conversation_history` on the next turn — no new session-state key), and an English-only rule (communicate ONLY in English — a non-English message gets a polite, concise English refusal with `action: null` rather than being fulfilled in any other language; this supersedes an earlier multilingual/Hebrew-specific-reply design) plus explicit build-intent disambiguation (any "build/assemble/configure a PC" phrasing is always intent 3, never redirected to Community) — all prompt-only, no runtime rejection, since these are style/UX concerns, not correctness ones. A real, confirmed correctness bug — the model occasionally echoing `current_build_context["components"]`'s `{"id","name","price_usd"}` object shape back into its own `load_build`/`modify_build` action's `components` field instead of the required `{category: int}` shape (especially on a second turn with `advisory_context` present) — is fixed authoritatively in Python, not just prompt wording: `_coerce_component_id_shapes(raw)` extracts the bare id from a recognizable `{"id": <int>, ...}` value before `ConciergeResponse.model_validate` runs. `ui/components/chat_assistant.py` also caps `conversation_history` to the last `_MAX_HISTORY_MESSAGES = 4` entries per call, bounding token cost on long conversations without trimming what's actually displayed. Not persisted to `llm_cache` (a free-form chat message has no stable build-state cache key). See `spec.md` §6.7/§7.8.
- `advisory.py` — a second, independent OpenRouter-backed feature: `get_build_advisory(...)` returns pros/cons of the current build (`pros`, `cons`) plus a structured, **machine-executable** in-budget optimization tip (`within_budget`) and stretch-budget upgrade suggestion (`stretch_budget`) — `within_budget.swaps` is a plain list of `{"action": "swap", "category", "replace_with_id"}`; `stretch_budget.actions` is a DISCRIMINATED UNION of that same swap shape OR `{"action": "set_quantity", "category": "RAM"|"Storage", "quantity"}`, so `ui/`'s "Apply" buttons (§7.4) can act directly rather than parsing text — and a stretch recommendation is no longer confined to swapping the single bottleneck category (see below). `stretch_budget`'s system-prompt objective and heuristic (`_heuristic_stretch_budget`) both now fall through a priority chain — bottleneck category, then GPU, then RAM quantity+1, then Storage quantity+1 (NVMe only), then Cooler, then every `engine.solvers.PERIPHERAL_CATEGORIES` category via `_try_peripheral_upgrade_or_add` — stopping at the first real, catalog-priced option, instead of giving up the moment the single bottleneck category alone has no headroom (a real bug that existed before this). Peripherals are a real, confirmed later addition to this chain (a live call returned `Delta: +€0.00` with real headroom left purely because nothing downstream ever considered an unselected Monitor/Keyboard/etc. as an option): `_try_peripheral_upgrade_or_add` treats an unselected peripheral as a genuine $0.0-baseline "first add," picking the single MOST EXPENSIVE real compatible option (unlike `_try_swap_upgrade`'s "cheapest step up," since there's no existing pick to step up from cheaply); `_catalog_alternatives` includes peripherals in the LLM's own payload the same way (`"current": null` for one not yet selected). `get_build_advisory` also cross-checks a validly-parsed but EMPTY `stretch_budget.actions` against this same heuristic before trusting it — an empty verdict isn't a hallucination Python can reject, but if the deterministic heuristic finds a real action the LLM missed, that action authoritatively replaces the LLM's empty one (source corrected to `"heuristic"`). Separate from `client.py`'s synergy/bottleneck/compatibility scoring (different question — "what should I change" vs "how good is what I have" — kept as a separate module rather than folded into `client.py`, matching this package's one-concern-per-file pattern). Follows `client.py`'s exact never-raises/`source`-tagged pattern (its own internal `AdvisoryUnavailableError`, never `LLMUnavailableError`). All four top-level content fields (and every nested `WithinBudgetAdvice`/`StretchBudgetAdvice` field) are REQUIRED on `BuildAdvisoryResponse` (no defaults) — a payload missing any of them fails validation and falls to the heuristic path; `swaps` being an empty list is fine (no beneficial swap found), that's not itself a failure. **Zero-hallucination id enforcement is authoritative in Python, not just prompt wording**: `_validate_advisory_actions` (internally `_check_swap`/`_check_quantity`) re-checks every `replace_with_id` against a fresh `engine.solvers.get_compatible_candidates(category, build_state)` call after parsing succeeds, raising `AdvisoryUnavailableError` (→ heuristic fallback) on any id/category that doesn't check out — the LLM is never trusted to have followed the "only real catalog ids" instruction on its own. **Extended to cost/direction for `stretch_budget` specifically** (a real, confirmed bug: a live call proposed swapping a GPU for the SAME component at a fabricated `+400 USD`, then a CHEAPER compatible GPU labeled an upgrade at another fabricated positive delta — `ui/components/chat_assistant.py`'s `use_remaining_budget` loop trusted `added_cost_usd` being non-zero as real progress and applied it unconditionally, silently making the build worse while leaving real RAM/Storage quantity headroom unexplored): every `stretch_budget` action's real price delta is recomputed directly from catalog data — a swap's real delta must be strictly positive (never lateral/backward), a `set_quantity`'s requested quantity must strictly exceed the current quantity — and `stretch_budget.added_cost_usd` must match the sum of those real deltas (small float tolerance aside); any mismatch raises the same `AdvisoryUnavailableError`. `within_budget.swaps` is not held to this same strict-increase invariant (a downgrade is its whole point — freeing budget for the bottlenecked side), so this check applies only to `stretch_budget.actions`. Real RAM/Storage slot-count math (real per-module math for RAM, real NVMe-only `m2_slots` for Storage) is NOT recomputed here: `_real_slot_count` is a thin wrapper delegating to `engine.compatibility.resolve_quantity_limit`, the one place in the codebase that owns this math — used by `_validate_advisory_actions`'s `set_quantity` guard and `_try_quantity_increment`'s heuristic fallthrough alike, so the LLM/heuristic path can never suggest a quantity the compatibility engine would then reject. `SYSTEM_PROMPT` has a distinct optimization objective per `mode` (Budget: stay within an internally-computed `remaining_budget`, only cost-neutral/paired swaps once maxed; Workload: align with `workload_profile` rather than any ceiling; Free: bottleneck mitigation and CPU/GPU platform balance), plus a strict-arithmetic rule requiring every stated price delta to exactly match a real catalog difference — mirrored deterministically in the heuristic fallback's per-mode wording and real swap-finding (`_heuristic_within_budget`/`_heuristic_stretch_budget` take `mode`/`profile`, return the same structured shape, and `_heuristic_within_budget` additively looks for a paired upgrade for the limiting category affordable within the exact savings its downgrade freed up). `remaining_budget` is derived from `build_state` (never a new parameter) and is `0.0` outside Budget mode. The system prompt also instructs the model to never use a standalone `$` in prices (write "600 USD" instead of "$600"), since a matching `$...$` pair in one Streamlit markdown string triggers KaTeX/math-mode rendering; `ui.format.sanitize_markdown` (a shared helper, not private to one view — also guards free-text like a community post title) is a client-side backstop for the same issue (now applied to `explanation`, not a raw string). Grounds its prompt in REAL catalog alternatives (current pick + a couple of cheaper/pricier compatible neighbors per category, each with its real `id`) fetched via `engine.solvers.get_compatible_candidates` — never `db.repositories.components_repo` directly, staying inside this package's allowed-imports boundary the same way `client.py`'s heuristic fallback does. Unlike `client.py`'s result, **not** persisted to `llm_cache` — this feature only has UI-session-level caching (`ui/views/create_build.py`'s `advisory_cache`), a deliberate scope decision since `llm_cache`'s schema/cache-key scheme is shaped for `analyze_build`'s request/response, not this one.

## Allowed imports
- `httpx`, `pydantic`.
- `engine.*` — to build the deterministic pre-check payload (`evaluate_build`, `bottleneck_percentage_baseline`) and to compute the heuristic fallback. This is a **read-only, compute-only** dependency — `llm/` calls `engine/` functions, never the reverse.
- `db.repositories.llm_cache_repo` — **only** this repository. No access to `users`, `builds`, or `components` tables from this package beyond what `engine/` already read.

## Forbidden
- No `streamlit` import — this package must be testable with mocked HTTP and no UI runtime.
- No compatibility/scoring logic duplicated here — always consume `engine/`'s output, never recompute or contradict it.
- No live network calls in tests — mock `httpx` responses.
- No silent failures with no signal at all: every failure path still produces a `BuildAnalysisResponse` with `source="heuristic"`, so `ui/` can always tell a real LLM answer from an estimate — the difference from earlier drafts of this doc is that the signal is a field on the return value, not a raised exception `ui/` must catch.

## Interface contract
```python
# client.py
class LLMUnavailableError(Exception): ...  # internal; analyze_build catches it, never lets it escape
def analyze_build(
    build_state: dict[str, Component],
    workload_profile: str | None = None,
    budget_ceiling: float | None = None,
) -> BuildAnalysisResponse: ...  # never raises; response.source tells you "llm" vs "heuristic"

# prompts.py
def build_request(build_state, workload_profile=None, budget_ceiling=None) -> BuildAnalysisRequest: ...

# cache.py
def cache_key(build_state: dict[str, Component], workload_profile: str | None, prompt_type: str = "build_analysis") -> str: ...

# advisory.py
class AdvisoryUnavailableError(Exception): ...  # internal; get_build_advisory catches it, never lets it escape
def get_build_advisory(
    build_state: dict[str, Component],
    mode: str,                            # "Budget" | "Workload" | "Free"
    current_budget_or_cost: float,        # Budget-mode ceiling if mode == "Budget", else current total cost
    profile: str | None = None,
    bottleneck_info: dict | None = None,  # computed via engine.scoring if omitted
    quantities: dict[str, int] | None = None,  # current RAM/Storage quantity, default 1 per category if omitted
) -> dict: ...  # never raises; {"pros": [str, ...], "cons": [str, ...],
                 #  "within_budget": {"explanation": str, "swaps": [{"action": "swap", "category": str, "replace_with_id": int}, ...], "can_optimize_further": bool},
                 #  "stretch_budget": {"explanation": str, "actions": [{"action": "swap", "category": str, "replace_with_id": int} | {"action": "set_quantity", "category": "RAM"|"Storage", "quantity": int}, ...], "added_cost_usd": float},
                 #  "source": "llm"|"heuristic"}

# concierge.py
class ConciergeUnavailableError(Exception): ...  # internal; get_concierge_response catches it, never lets it escape
def get_concierge_response(
    user_message: str,
    conversation_history: list[dict],  # [{"role": "user"|"assistant", "content": str}, ...], most recent last
    catalog_summary: list[dict],       # ALL catalog components, pre-fetched by the caller (ui/)
    community_summary: list[dict],     # every currently-shared community post, pre-fetched by the caller (ui/)
    current_build_context: dict | None = None,  # {"mode", "budget_ceiling": float|None, "components": {cat: {"id","name","price_usd","display_price"}}, "quantities", "formatted_total": str, "compatibility_issues": [str,...], "bottleneck": {"percentage": float, "direction": "CPU-bound"|"GPU-bound"|"Balanced"}|None} snapshot of the active build_draft, or None
    advisory_context: dict | None = None,  # caller-fetched get_build_advisory() result {"pros","cons","within_budget","stretch_budget","source"}, or None/{} if none computed yet
    drafts_summary: list[dict] | None = None,           # [{"draft_id","name","mode"}, ...] the user's own draft_builds rows
    previous_builds_summary: list[dict] | None = None,  # [{"build_id","name","creation_mode"}, ...] the user's own builds rows
    current_page: str | None = None,   # raw st.session_state["page"] — lets the model resolve page-relative phrasing
    viewed_post_id: int | None = None, # st.session_state["selected_post_id"], only sent when current_page == "community"
    active_currency: str = "USD",      # st.session_state["selected_currency"] — see CURRENCY AWARENESS above; the
                                        # model quotes catalog_summary/community_summary's own display_price/
                                        # display_total_cost verbatim instead of converting price_usd/total_cost itself
    currency_rates: dict[str, float] | None = None,  # ui.format.CURRENCY_RATES, e.g. {"USD":1.0,"EUR":0.92,"NIS":3.70}
                                        # — the ONE currency-math exception: converting a budget FIGURE STATED IN
                                        # THE USER'S MESSAGE to USD before picking parts (intent 3's BUDGET
                                        # CURRENCY CONVERSION rule), never for quoting a price back to the user
) -> dict: ...  # never raises; {"reply": str (<=2 sentences, prompt-only enforced),
                 #  "action": {"type": "load_build", "components": {category: id}, "budget_cap_usd": float|None, "explanation": str}
                 #          | {"type": "modify_build", "components": {category: id}, "quantities": {category: int}, "explanation": str}
                 #          | {"type": "navigate", "navigate_to": "landing"|"create_build"|"my_builds"|"community"|"drafts",
                 #             "filters": {"build_type": "All"|"Budget"|"Workload"|"Free", "max_price": float|None,
                 #                         "domain": str|None, "tier": str|None} | None,
                 #             "reset_mode": bool}  # only meaningful with navigate_to == "create_build"
                 #          | {"type": "save_build", "name": str, "destination": "draft"|"build",
                 #             "publish_immediately": bool, "author_notes": str | None,
                 #             "source": "studio"|"community", "source_post_id": int | None, "explanation": str}
                 #          | {"type": "publish_build", "author_notes": str | None}
                 #          | {"type": "open_community_build", "post_id": int}
                 #          | {"type": "load_saved_build", "source": "draft"|"build"|"community", "id": int}
                 #          | {"type": "fix_warnings", "explanation": str}
                 #          | {"type": "optimize_bottleneck", "target_percentage": float|None, "explanation": str}
                 #          | None,
                 #  "currency_switch": "USD"|"EUR"|"NIS"|None,  # top-level, co-occurs with any action above
                 #  "source": "llm" | "heuristic"}
```
Bounding rule from `spec.md` §6.3: the LLM-refined `bottleneck.bottleneck_percentage` must stay within the request's `deterministic_precheck.baseline_bottleneck_percentage` ± 10 percentage points.
