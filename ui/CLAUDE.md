# ui/ — Scoped Guardrails

See root `CLAUDE.md` and `spec.md` §7 before editing here.

## Responsibility
All Streamlit rendering, page routing, and session-state orchestration. This package is the only one allowed to import `streamlit` broadly (aside from `auth/session.py`'s narrow exception). It contains no SQL and no compatibility/scoring/solver math — it calls into `auth/`, `engine/`, `db/repositories/`, and `llm/` and renders their results.

## Files
- `router.py` — reads `st.session_state["page"]`, dispatches to the matching `views/*.py::render()`. Enforces the auth hard-gate: unauthenticated users are always forced to `landing` regardless of requested page (`spec.md` §7.2).
- `state.py` — the single source of truth for `st.session_state` shape: `init_session_state()` (defaults, called once from `app.py`), `navigate_to_page(target_page)` (every real page transition — `app.py`'s sidebar buttons, the Concierge's `navigate` action — routes through this instead of a raw `st.session_state["page"] = ...` assignment; its one added behavior is resetting `selected_post_id` to `None` whenever `target_page == "community"`, so a stale single-post thread view never resurfaces after navigating back to the feed from elsewhere), `teardown_builder()` (spec.md §7.9 — the single source of truth for leaving Build Studio: performs NO database write of any kind, it unconditionally resets `create_mode`/`build_draft`/`build_draft_analysis`/`has_unsaved_build_changes`; an unsaved build not explicitly checkpointed via the "Save as draft" checkbox (§7.4 step 9) is simply discarded, same tradeoff as closing the tab. Called by every real exit vector: `app.py`'s sidebar nav buttons and Logout, `views/create_build.py`'s "⬅ Change mode" button, and `components/chat_assistant.py`'s Concierge `navigate`/`open_community_build`/`reset_mode` handling. Does not itself touch `page` or log out — callers do that immediately after), `new_build_draft()`, and the `build_draft` (plain dict, category -> component **id**) <-> `BuildState` (category -> `Component` row) bridge: `resolve_build_state`, `set_component`, `remove_component` (both also clear `build_draft_analysis` via `_invalidate_analysis` — a component change always makes the last synergy/bottleneck read stale), `build_total_cost(build_state, quantities=None)`. `get_quantity(build_draft, category)`/`set_quantity(build_draft, category, quantity)` own `build_draft["quantities"]` (a `dict[str, int]`, meaningful only for `"RAM"`/`"Storage"` — every other category is implicitly quantity 1): `set_quantity` clamps to a minimum of 1 and also invalidates analysis like a component swap does; `remove_component` clears the category's stored quantity too, so a re-filled slot starts back at 1x.
- `theme.py` — the single source of color/typography constants (`spec.md` §7.7) plus `inject_css()` and `tag(text, kind)` for colored inline spans (danger/success/warning). Status badges (e.g. `part_picker.py`'s "Selected"/"Empty") use the native `st.badge` widget instead, not a `theme.*` helper. No hex codes or font sizes hardcoded in any `views/` or `components/` file — import from here. Also locks the sidebar (`spec.md` §7.7): hides `[data-testid="stSidebarCollapseButton"]` (a `<div>`, not a `<button>` despite the name — confirmed live) and pins `section[data-testid="stSidebar"]` to 320px via `width`/`min-width`/`max-width` all together, `!important` — `width` alone is load-bearing here since Streamlit's own resize logic writes a non-important inline `width` that only an `!important` `width` rule (not `min-width`/`max-width` alone) reliably beats.
- `format.py` — tiny shared display-formatting helpers (e.g. `humanize_profile("VideoEditing") -> "Video Editing"`; `sanitize_markdown(text) -> text.replace("$", "USD ")`, defending against Streamlit's KaTeX/math-mode rendering when a matching `$...$` pair appears in one markdown string — used for LLM-authored advisory text in `create_build.py` and for free-text content like a community post title combined with an appended price in `community.py`). Purely string formatting, no business logic.
- `views/landing.py`, `views/create_build.py`, `views/my_builds.py`, `views/community.py`, `views/drafts.py` — one file per top-level page. `drafts.py` (`spec.md` §7.9, page key `"drafts"`) lists the current user's `draft_builds` (`db.repositories.drafts_repo.get_user_drafts`) as plain cards with "Load into Builder"/"Delete" actions — not a `render_build_card` call, since a draft is not a full scored `Build` row. `community.py`'s `_thread_view` component list shows a `(x{N})` badge after the category label when `BuildComponent.quantity > 1` (`spec.md` §7.6), with the displayed price being the real per-line total (`unit price × quantity`).
- `components/chat_assistant.py` — the AI Concierge sidebar widget (`spec.md` §7.8), rendered from `app.py`'s sidebar for authenticated users only. Owns all context-assembly for `llm.concierge` (the full catalog, the community feed, a snapshot of the active `build_draft` including its `budget_ceiling`, and — gated behind a cheap local keyword heuristic, `_looks_like_analysis_request` — a pre-fetched `get_build_advisory` result reusing `advisory_cache`) and applies any `load_build`/`modify_build`/`navigate`/`open_community_build` action it gets back IMMEDIATELY — no confirmation click, since none of them touch the database at all (`load_build`/`modify_build`/`navigate` only ever mutate the uncommitted `build_draft`/`page`; `open_community_build` only sets `page`/`selected_post_id`). `navigate_to` accepts 5 real page keys, including `"drafts"`. **Builder teardown, no database write** (spec.md §7.9): a `navigate` action leaving `create_build` for a different page calls `ui.state.teardown_builder()` first — the SAME function `app.py`'s sidebar buttons/Logout and `views/create_build.py`'s "⬅ Change mode" button call — which resets the builder's session state with no draft ever created (an earlier silent-auto-save-on-exit design, and an even earlier "Save Draft or Discard?" dialog, `ui/components/nav_guard.py`, have both been removed entirely — a later, explicit product decision: the "Save as draft" checkbox in the manual Save UI is now the single source of truth for creating a draft). **`reset_mode`** (optional bool, only meaningful with `navigate_to == "create_build"`) exposes the "⬅ Change mode" button via chat — the identical `teardown_builder()` call. `open_community_build` also calls it first when leaving `create_build`, since deep-linking away is still leaving the builder. A `navigate` action's other optional refinement: a non-empty `filters` payload is staged into the one-shot `st.session_state["pending_community_filters"]` key (a name deliberately distinct from `ui/views/community.py`'s own real `community_mode_filter`/`community_price_filter`/`community_domain_filter`/`community_tier_filter` widget keys — this module cannot resolve a requested filter into one of those real, live-data-dependent option strings itself) for that view's `_apply_pending_community_filters` to translate on its next render. `open_community_build` deep-links straight to one specific, already-shared community post's thread view: `action["post_id"]` (a real `CommunityPost.id`, already zero-hallucination-guarded by `llm/concierge.py` against the exact `community_summary` this module sent it — never a `Build.id`) is written directly to `st.session_state["selected_post_id"]` alongside `st.session_state["page"] = "community"`; `ui/views/community.py::render()` already checks `selected_post_id` at the very top of its own function, so no changes were needed there for this to land on the post's thread view on the very next render. `save_build` is deliberately NOT zero-click (a reversal of an earlier "fire immediately with an auto-generated name" design): the Concierge must first ask the user for both a `name` and a `destination` (`"draft"` or `"build"`) and wait for their answer across one or more turns — enforced structurally by both fields being REQUIRED on `llm.schemas.ConciergeSaveBuildAction` — before this module ever receives the action. Once it does arrive, it (and a later `publish_build`) is still applied immediately with no separate Python-level confirmation click, and DOES write to the database right away: `destination == "draft"` calls `db.repositories.drafts_repo.save_draft` (the real `draft_builds` table — there is no `saved_builds` table); `destination == "build"` calls `builds_repo.create_build`, matching `ui/views/create_build.py::_save_actions`'s own real call shape exactly, and — on a later `publish_build` turn (reachable only after a `"build"`-destination save) — `builds_repo.set_public` + `community_repo.create_post`. This is judged safe specifically because it's the user's own explicit request acting on their own account's own data, the same trust boundary as them clicking "Save build" themselves. Both `save_build` branches leave `build_draft`/`create_mode`/`page` untouched (a deliberate choice — see the module's own docstring) and use the user's own literal `name` (never an auto-generated one — `_default_saved_build_name()` is now only a last-resort defensive fallback); only the `"build"` branch stores the new build's id/name in `st.session_state["concierge_last_saved_build"]`, the one piece of real state the LLM cannot know on its own and that a later `publish_build` action (which carries no build id itself) needs to resolve which build to publish — a `"draft"` save never sets it, since a draft has no publish path.
- `components/auth_modal.py`, `components/build_card.py`, `components/part_picker.py` — reusable widgets shared across views. `build_card.py`'s `render_build_card(..., confirm_labels=frozenset({"Delete"}))` gates any action named in `confirm_labels` behind a Yes/Cancel step before its callback fires — use this for any future destructive action, not just Delete. `part_picker.py` renders each slot as a status-badged card with a `st.popover` drawer (not `st.expander`) for changing the pick, plus a slot-level `"✕"` clear button (`key=f"clear_{category}"`) next to the popover trigger — not inside the drawer — so a filled slot can be emptied in one click; the drawer itself holds only the candidate list, no bottom "Remove" button. For `"RAM"`/`"Storage"` specifically, when a component is selected, `render_part_picker`'s optional `quantity`/`on_quantity_change`/`quantities` params add a compact `st.number_input("Qty", ...)` stepper right below the price/specs caption (price caption switches to a `price × qty = total` format once qty > 1) — the stepper's `max_value` comes from `ui.state.resolve_effective_quantity_limit(build_state, category, quantities, budget_ceiling)`, NOT a duplicated/independent calculation. That function returns `(effective_max, reason, limit_kind)`, combining the real physical limit (`engine.compatibility.resolve_quantity_limit` — real per-module RAM math, real `m2_slots` for NVMe Storage) with a budget-affordability limit (only when `budget_ceiling` is not `None`, i.e. Budget mode) and picking whichever is tighter: `limit_kind == "physical"` shows the motherboard-derived caption, `"budget"` shows a distinct budget-ceiling caption (and the widget's `max_value` itself blocks the increment before it happens, not just a post-hoc warning), `"none"` falls back to a UI-only `_FALLBACK_QUANTITY_CAP = 4` — honestly captioned as a generic safety cap, never presented as a motherboard-specific fact (e.g. SATA storage, which has no real port-count data anywhere in this catalog). Before rendering the widget, any stale `st.session_state[f"qty_{category}"]` value exceeding the newly-computed max is clamped down first — a real Streamlit gotcha: a keyed widget ignores its `value=` argument on every rerun after the first and instead uses whatever's already in session state, so if the effective limit shrinks (from either the physical or budget side) without this pre-clamp, `st.number_input` raises a raw `StreamlitAPIException` instead of silently re-clamping. **Fixed** (was tracked as a known gap): `ui.state.set_quantity`/`remove_component` now sync the stepper's own widget key directly (`_sync_qty_widget_key`, `ui/state.py`) whenever the real quantity changes — the SINGLE source of truth for `qty_{category}`'s naming convention now lives in `ui/state.py` itself rather than requiring every out-of-band caller (the AI Concierge's `modify_build` quantity handling, the advisory's stretch-upgrade `set_quantity` action) to know it. The one wrinkle: Streamlit forbids writing to (or popping) a widget's session-state key AFTER that widget has already been instantiated in the CURRENT script run (`StreamlitWidgetAlreadyInstantiatedError`) — this fires for real when `set_quantity` is called from the stepper's OWN on-change callback (the widget already rendered earlier in this same run, using the just-typed value) or from create_build.py code that runs after the part-picker grid. `_sync_qty_widget_key` silently swallows exactly that one exception in exactly that context — harmless, since in the on-change case the write would be redundant anyway (the widget's own interaction already put the same value there), and in the after-the-grid case `build_draft["quantities"]` is already correct and gets picked up on the very next fresh render, before that key's widget has instantiated in that new run. No other category gets this control.

## Allowed imports
- `streamlit`.
- `auth.service`, `auth.session`.
- `engine.*` (compatibility, solvers, scoring) — for computing what to display, never to persist.
- `db.repositories.*` — for reading/writing builds, components, community data.
- `llm.client` — for build analysis display. `analyze_build(...)` never raises (see `llm/CLAUDE.md`), so there is no fallback branch to write here. `response.source` (`"llm"` vs `"heuristic"`) is still on every response, even though the summary banner no longer surfaces it as a badge — a future view is free to read it again.
- `llm.advisory` — for the "✨ Get AI Analysis & Upgrade Path" advisory. `get_build_advisory(...)` also never raises; its `["source"]` key IS surfaced (a `st.caption` inside the advisory expander), unlike `analyze_build`'s badge.
- `llm.concierge` — for the sidebar AI Concierge (`components/chat_assistant.py`). `get_concierge_response(...)` also never raises; its `action` (when present) is applied immediately by the caller with no confirmation step (see `spec.md` §7.8 for why that's safe here).

## Forbidden
- No SQL, no SQLAlchemy imports — go through `db.repositories`.
- No compatibility/scoring math inlined in a view — call `engine/`.
- No direct `httpx`/OpenRouter calls — go through `llm.client`.
- No view may bypass the auth gate in `router.py` by setting `st.session_state["page"]` directly to a gated page without an `auth_user` present.

## State ownership
Own and mutate only the `st.session_state` keys listed in `spec.md` §7.1 (`page`, `auth_user`, `auth_mode`, `auth_error`, `create_mode`, `build_draft`, `build_draft_analysis`, `advisory_cache`, `stretch_applied_keys`, `sort_criteria`, `previous_builds_filter`, `selected_post_id`, `fork_source_build_id`, `concierge_messages`, `has_unsaved_build_changes`, `concierge_last_saved_build`, `pending_community_filters`), and prefer the helpers in `state.py` over raw dict writes scattered across view files. `auth_user`/`auth_mode`/`auth_error` should be mutated only via `auth.session` helpers (`log_in`, `log_out`, `set_auth_mode`), never as raw dict writes. `concierge_last_saved_build` (`{"build_id": int, "name": str} | None`) is owned entirely by `components/chat_assistant.py`: set when a Concierge `save_build` action with `destination == "build"` is applied (never set for `destination == "draft"` — a draft has no publish path), read (never popped — a later `"build"`-destination `save_build` in the same session simply overwrites it) when a later `publish_build` action needs to know which real build to publish. Deliberately a distinctly-named key, not a reuse of the retired `concierge_pending_action` key from an unrelated, now-removed confirm-before-apply mechanism. `pending_community_filters` (`dict | None`, not in `_DEFAULTS` — an ad-hoc key that only exists once a Concierge navigation-with-filters action has actually fired) is written only by `components/chat_assistant.py` (a Concierge `navigate` action's `filters` payload) and consumed (popped, one-shot) only by `views/community.py::_apply_pending_community_filters` — neither module writes to the other's real widget keys (`community_mode_filter`/`community_price_filter`/`community_domain_filter`/`community_tier_filter`) directly, since only `community.py`, at render time, has the live feed data needed to resolve a requested filter into one of those widgets' real options safely.

## LLM debounce/cache contract
`llm.client.analyze_build(...)` already checks `llm_cache` internally before calling OpenRouter — `ui/` doesn't need to compute the cache key itself. What `ui/` *is* responsible for: not calling `analyze_build` on every single part-picker rerun. `create_build.py`'s `_maybe_auto_analyze` is the one deliberate exception to "gate behind an explicit click" — by product decision, it auto-calls `analyze_build` the instant a build first becomes complete (all 8 core categories filled), across every creation mode. This is still bounded, not "every rerun": the trigger condition is `build_draft_analysis is None AND build is complete`, and `ui/state.py`'s `set_component`/`remove_component` only set `build_draft_analysis` to `None` on an actual component change — so a rerun that doesn't change the build (opening a popover, adjusting an unrelated widget) never re-fires it. (The summary banner's old compact "🔮 Analyze" manual-retrigger button was removed in a later round by explicit product decision — there is no manual re-trigger for `analyze_build` anymore, only the automatic one.)

`llm.advisory.get_build_advisory(...)` has NO persistent `llm_cache` entry of its own (a deliberate scope decision — see `llm/CLAUDE.md`) and is never auto-triggered — it stays behind the explicit "✨ Get AI Analysis & Upgrade Path" button (`create_build.py`'s `_advisory_controls`) on every click, since unlike the synergy/bottleneck read it isn't part of "what a complete build inherently has," it's an on-demand deeper analysis. Its ONLY caching layer is `st.session_state["advisory_cache"]`, a plain dict keyed by `(sorted (category, component.id) pairs, mode, current_budget_or_cost)` — computed fresh (not stored in a session-state slot) on every render from the CURRENT build, so a cache hit needs no re-click and a build/mode/cost change simply has no entry yet (no stale display, no manual invalidation needed).

**Any test that drives `create_build.py`/the Concierge widget through `streamlit.testing.v1.AppTest`** must neutralize all three LLM entry points (`analyze_build`, `get_build_advisory`, AND `get_concierge_response`) — e.g. `monkeypatch.delenv("OPENROUTER_API_KEY", raising=False)` AFTER importing `db.database` (its module-level `load_dotenv()` repopulates `os.environ` from a real `.env` at import time, so clearing the var before that import is a no-op — a real bug caught during this feature's own development), ideally as an autouse fixture — otherwise a real `.env` key present in the test process turns nearly every UI smoke test that completes a build into a live, billed OpenRouter call, violating this project's "no live network calls in tests" rule. See `tests/test_ui_smoke.py`'s `_no_live_llm_calls` autouse fixture.
