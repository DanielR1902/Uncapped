# ui/ — Scoped Guardrails

See root `CLAUDE.md` and `spec.md` §7 before editing here.

## Responsibility
All Streamlit rendering, page routing, and session-state orchestration. This package is the only one allowed to import `streamlit` broadly (aside from `auth/session.py`'s narrow exception). It contains no SQL and no compatibility/scoring/solver math — it calls into `auth/`, `engine/`, `db/repositories/`, and `llm/` and renders their results.

## Files
- `router.py` — reads `st.session_state["page"]`, dispatches to the matching `views/*.py::render()`. Enforces the auth hard-gate: unauthenticated users are always forced to `landing` regardless of requested page (`spec.md` §7.2).
- `state.py` — the single source of truth for `st.session_state` shape: `init_session_state()` (defaults, called once from `app.py`), `new_build_draft()`, and the `build_draft` (plain dict, category -> component **id**) <-> `BuildState` (category -> `Component` row) bridge: `resolve_build_state`, `set_component`, `remove_component` (both also clear `build_draft_analysis` via `_invalidate_analysis` — a component change always makes the last synergy/bottleneck read stale), `build_total_cost(build_state, quantities=None)`. `get_quantity(build_draft, category)`/`set_quantity(build_draft, category, quantity)` own `build_draft["quantities"]` (a `dict[str, int]`, meaningful only for `"RAM"`/`"Storage"` — every other category is implicitly quantity 1): `set_quantity` clamps to a minimum of 1 and also invalidates analysis like a component swap does; `remove_component` clears the category's stored quantity too, so a re-filled slot starts back at 1x.
- `theme.py` — the single source of color/typography constants (`spec.md` §7.7) plus `inject_css()` and `tag(text, kind)` for colored inline spans (danger/success/warning). Status badges (e.g. `part_picker.py`'s "Selected"/"Empty") use the native `st.badge` widget instead, not a `theme.*` helper. No hex codes or font sizes hardcoded in any `views/` or `components/` file — import from here.
- `format.py` — tiny shared display-formatting helpers (e.g. `humanize_profile("VideoEditing") -> "Video Editing"`; `sanitize_markdown(text) -> text.replace("$", "USD ")`, defending against Streamlit's KaTeX/math-mode rendering when a matching `$...$` pair appears in one markdown string — used for LLM-authored advisory text in `create_build.py` and for free-text content like a community post title combined with an appended price in `community.py`). Purely string formatting, no business logic.
- `views/landing.py`, `views/create_build.py`, `views/my_builds.py`, `views/community.py` — one file per top-level page, matching `spec.md` §7.4–§7.6.
- `components/chat_assistant.py` — the AI Concierge sidebar widget (`spec.md` §7.8), rendered from `app.py`'s sidebar for authenticated users only. Owns all context-assembly for `llm.concierge` (the full catalog, the community feed, and a snapshot of the active `build_draft`) and applies any `load_build`/`modify_build`/`navigate` action it gets back IMMEDIATELY — no confirmation click, since it only ever mutates the uncommitted `build_draft`, never the database directly.
- `components/auth_modal.py`, `components/build_card.py`, `components/part_picker.py` — reusable widgets shared across views. `build_card.py`'s `render_build_card(..., confirm_labels=frozenset({"Delete"}))` gates any action named in `confirm_labels` behind a Yes/Cancel step before its callback fires — use this for any future destructive action, not just Delete. `part_picker.py` renders each slot as a status-badged card with a `st.popover` drawer (not `st.expander`) for changing the pick, plus a slot-level `"✕"` clear button (`key=f"clear_{category}"`) next to the popover trigger — not inside the drawer — so a filled slot can be emptied in one click; the drawer itself holds only the candidate list, no bottom "Remove" button. For `"RAM"`/`"Storage"` specifically, when a component is selected, `render_part_picker`'s optional `quantity`/`on_quantity_change`/`quantities` params add a compact `st.number_input("Qty", ...)` stepper right below the price/specs caption (price caption switches to a `price × qty = total` format once qty > 1) — the stepper's `max_value` comes from `ui.state.resolve_effective_quantity_limit(build_state, category, quantities, budget_ceiling)`, NOT a duplicated/independent calculation. That function returns `(effective_max, reason, limit_kind)`, combining the real physical limit (`engine.compatibility.resolve_quantity_limit` — real per-module RAM math, real `m2_slots` for NVMe Storage) with a budget-affordability limit (only when `budget_ceiling` is not `None`, i.e. Budget mode) and picking whichever is tighter: `limit_kind == "physical"` shows the motherboard-derived caption, `"budget"` shows a distinct budget-ceiling caption (and the widget's `max_value` itself blocks the increment before it happens, not just a post-hoc warning), `"none"` falls back to a UI-only `_FALLBACK_QUANTITY_CAP = 4` — honestly captioned as a generic safety cap, never presented as a motherboard-specific fact (e.g. SATA storage, which has no real port-count data anywhere in this catalog). Before rendering the widget, any stale `st.session_state[f"qty_{category}"]` value exceeding the newly-computed max is clamped down first — a real Streamlit gotcha: a keyed widget ignores its `value=` argument on every rerun after the first and instead uses whatever's already in session state, so if the effective limit shrinks (from either the physical or budget side) without this pre-clamp, `st.number_input` raises a raw `StreamlitAPIException` instead of silently re-clamping. **Known gap**: this same mechanism means any quantity change written to `build_draft["quantities"]` from OUTSIDE this widget's own callback (e.g. a stretch-upgrade `set_quantity` advisory action) can be silently reverted by the stepper's stale session-state key on its very next render — `ui.state.set_quantity` has no way to also clear/sync the widget's key, since it doesn't know the `qty_{category}` naming convention. Not yet fixed; tracked as a follow-up. No other category gets this control.

## Allowed imports
- `streamlit`.
- `auth.service`, `auth.session`.
- `engine.*` (compatibility, solvers, scoring) — for computing what to display, never to persist.
- `db.repositories.*` — for reading/writing builds, components, community data.
- `llm.client` — for build analysis display. `analyze_build(...)` never raises (see `llm/CLAUDE.md`), so there is no fallback branch to write here. `response.source` (`"llm"` vs `"heuristic"`) is still on every response, even though the summary banner no longer surfaces it as a badge — a future view is free to read it again.
- `llm.advisory` — for the "✨ Get AI Analysis & Upgrade Path" advisory. `get_build_advisory(...)` also never raises; its `["source"]` key IS surfaced (a `st.caption` inside the advisory expander), unlike `analyze_build`'s badge.
- `llm.concierge` — for the sidebar AI Concierge (`components/chat_assistant.py`). `get_concierge_response(...)` also never raises; its `action` (when present) is applied immediately by the caller with no confirmation step (see `spec.md` §7.8 for why that's safe here).

## Forbidden
- No SQL, no SQLAlchemy imports — go through `db.repositories`.
- No compatibility/scoring math inlined in a view — call `engine/`.
- No direct `httpx`/OpenRouter calls — go through `llm.client`.
- No view may bypass the auth gate in `router.py` by setting `st.session_state["page"]` directly to a gated page without an `auth_user` present.

## State ownership
Own and mutate only the `st.session_state` keys listed in `spec.md` §7.1 (`page`, `auth_user`, `auth_mode`, `auth_error`, `create_mode`, `build_draft`, `build_draft_analysis`, `advisory_cache`, `stretch_applied_keys`, `sort_criteria`, `previous_builds_filter`, `selected_post_id`, `fork_source_build_id`, `concierge_messages`), and prefer the helpers in `state.py` over raw dict writes scattered across view files. `auth_user`/`auth_mode`/`auth_error` should be mutated only via `auth.session` helpers (`log_in`, `log_out`, `set_auth_mode`), never as raw dict writes.

## LLM debounce/cache contract
`llm.client.analyze_build(...)` already checks `llm_cache` internally before calling OpenRouter — `ui/` doesn't need to compute the cache key itself. What `ui/` *is* responsible for: not calling `analyze_build` on every single part-picker rerun. `create_build.py`'s `_maybe_auto_analyze` is the one deliberate exception to "gate behind an explicit click" — by product decision, it auto-calls `analyze_build` the instant a build first becomes complete (all 8 core categories filled), across every creation mode. This is still bounded, not "every rerun": the trigger condition is `build_draft_analysis is None AND build is complete`, and `ui/state.py`'s `set_component`/`remove_component` only set `build_draft_analysis` to `None` on an actual component change — so a rerun that doesn't change the build (opening a popover, adjusting an unrelated widget) never re-fires it. (The summary banner's old compact "🔮 Analyze" manual-retrigger button was removed in a later round by explicit product decision — there is no manual re-trigger for `analyze_build` anymore, only the automatic one.)

`llm.advisory.get_build_advisory(...)` has NO persistent `llm_cache` entry of its own (a deliberate scope decision — see `llm/CLAUDE.md`) and is never auto-triggered — it stays behind the explicit "✨ Get AI Analysis & Upgrade Path" button (`create_build.py`'s `_advisory_controls`) on every click, since unlike the synergy/bottleneck read it isn't part of "what a complete build inherently has," it's an on-demand deeper analysis. Its ONLY caching layer is `st.session_state["advisory_cache"]`, a plain dict keyed by `(sorted (category, component.id) pairs, mode, current_budget_or_cost)` — computed fresh (not stored in a session-state slot) on every render from the CURRENT build, so a cache hit needs no re-click and a build/mode/cost change simply has no entry yet (no stale display, no manual invalidation needed).

**Any test that drives `create_build.py`/the Concierge widget through `streamlit.testing.v1.AppTest`** must neutralize all three LLM entry points (`analyze_build`, `get_build_advisory`, AND `get_concierge_response`) — e.g. `monkeypatch.delenv("OPENROUTER_API_KEY", raising=False)` AFTER importing `db.database` (its module-level `load_dotenv()` repopulates `os.environ` from a real `.env` at import time, so clearing the var before that import is a no-op — a real bug caught during this feature's own development), ideally as an autouse fixture — otherwise a real `.env` key present in the test process turns nearly every UI smoke test that completes a build into a live, billed OpenRouter call, violating this project's "no live network calls in tests" rule. See `tests/test_ui_smoke.py`'s `_no_live_llm_calls` autouse fixture.
