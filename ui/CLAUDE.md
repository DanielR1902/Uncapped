# ui/ — Scoped Guardrails

See root `CLAUDE.md` and `spec.md` §7 before editing here.

## Responsibility
All Streamlit rendering, page routing, and session-state orchestration. This package is the only one allowed to import `streamlit` broadly (aside from `auth/session.py`'s narrow exception). It contains no SQL and no compatibility/scoring/solver math — it calls into `auth/`, `engine/`, `db/repositories/`, and `llm/` and renders their results.

## Files
- `app.py` (repo root, not inside `ui/` itself, but this is where its rendering logic is documented since it's the Streamlit entrypoint tightly coupled to `ui/`'s own state/session helpers) — sidebar-only orchestration, no business logic (its own module docstring says so): renders the authenticated user's name, the currency selector, the 5 nav buttons, the AI Concierge widget, and Logout, gated behind `st.session_state.get("auth_user")`. **The currency selector's POSITION is load-bearing** (`spec.md` §7.10): `st.selectbox("Currency", ..., key="selected_currency")` is rendered BEFORE the nav-buttons loop, not after — confirmed live that a keyed widget positioned AFTER code that can call `st.rerun()` mid-script (every nav button does, immediately upon a match) loses track of its own prior session-state value the next time it's reached (falling back to its `index=0` default) if it was skipped by that earlier `st.rerun()` on the intervening pass. Placing it ahead of any such early-exit control sidesteps the whole class of bug, since it's then reached on every single script pass regardless of what else fires. **Immediately before that selectbox instantiates**, `app.py` also resolves the one-shot `pending_currency_switch` staging key (popped, copied into `selected_currency`) — the Concierge's own `currency_switch` response field (§6.7/§7.10) lands here, since `components/chat_assistant.py` cannot write `selected_currency` directly (that widget already rendered earlier in the pass it's called from — `StreamlitWidgetAlreadyInstantiatedError`).
- `router.py` — reads `st.session_state["page"]`, dispatches to the matching `views/*.py::render()`. Enforces the auth hard-gate: unauthenticated users are always forced to `landing` regardless of requested page (`spec.md` §7.2).
- `state.py` — the single source of truth for `st.session_state` shape: `init_session_state()` (defaults, called once from `app.py`), `navigate_to_page(target_page)` (every real page transition — `app.py`'s sidebar buttons, the Concierge's `navigate` action — routes through this instead of a raw `st.session_state["page"] = ...` assignment; its one added behavior is resetting `selected_post_id` to `None` whenever `target_page == "community"`, so a stale single-post thread view never resurfaces after navigating back to the feed from elsewhere), `teardown_builder()` (spec.md §7.9 — the single source of truth for leaving Build Studio: performs NO database write of any kind, it unconditionally resets `create_mode`/`build_draft`/`build_draft_analysis`/`has_unsaved_build_changes`; an unsaved build not explicitly checkpointed via the "Save as draft" checkbox (§7.4 step 9) is simply discarded, same tradeoff as closing the tab. Called by every real exit vector: `app.py`'s sidebar nav buttons and Logout, `views/create_build.py`'s "⬅ Change mode" button, and `components/chat_assistant.py`'s Concierge `navigate`/`open_community_build`/`reset_mode`/`load_saved_build` handling. Does not itself touch `page` or log out — callers do that immediately after), `new_build_draft()`, `load_components_into_new_draft(mode, components, quantities=None, name="")` (the shared shape every "load an existing build/draft into the studio" entry point needs: builds a fresh `new_build_draft(mode)` and replays `components`/`quantities` through the real `set_component`/`set_quantity` setters rather than raw dict writes, so `has_unsaved_build_changes` and analysis-invalidation fire correctly as a side effect; used by `views/drafts.py::_load_into_builder`, `views/community.py::_fork_into_studio`, `views/my_builds.py::_clone_into_studio`, and `components/chat_assistant.py`'s `load_saved_build` handler — the single common helper behind all 4 "open this saved thing in the Studio" call sites), and the `build_draft` (plain dict, category -> component **id**) <-> `BuildState` (category -> `Component` row) bridge: `resolve_build_state`, `set_component`, `remove_component` (both also clear `build_draft_analysis` via `_invalidate_analysis` — a component change always makes the last synergy/bottleneck read stale), `build_total_cost(build_state, quantities=None)`. `get_quantity(build_draft, category)`/`set_quantity(build_draft, category, quantity)` own `build_draft["quantities"]` (a `dict[str, int]`, meaningful only for `"RAM"`/`"Storage"` — every other category is implicitly quantity 1): `set_quantity` clamps to a minimum of 1 and also invalidates analysis like a component swap does; `remove_component` clears the category's stored quantity too, so a re-filled slot starts back at 1x. `resolve_effective_quantity_limit(build_state, category, quantities, budget_ceiling, currency="USD")` (`spec.md` §7.10) takes an optional `currency` param purely for its own `financial_reason` string's display formatting (via `ui.format.format_currency`) — `budget_ceiling` itself is always compared in real USD regardless of what's passed here.

the `"community"` source also sets `fork_source_build_id` like a manual fork would. `save_build` is deliberately NOT zero-click on the FIRST mention of an incomplete request (a reversal of an earlier "fire immediately with an auto-generated name" design): the Concierge must have both a `name` and a `destination` (`"draft"` or `"build"`) — enforced structurally by both fields being REQUIRED on `llm.schemas.ConciergeSaveBuildAction` — before this module ever receives the action, asking across one or more turns for whichever piece is missing. If the user's OWN message already supplied everything up front (a "fast-track" message, e.g. "save this as draft named Beast Rig" or "save as workstation and publish to community"), the SYSTEM_PROMPT fires the action on that very first turn instead of asking anything it doesn't need to — no separate Python-level change was needed for this, it's entirely a prompt-level intent-extraction improvement in `llm/concierge.py`. Once the action arrives, it first resolves WHICH build's data gets persisted via `action["source"]` (`"studio"`, the default and unchanged behavior — `st.session_state["build_draft"]` — or `"community"`, a SEPARATE refinement covering a request like "save the build I'm looking at to my drafts" made while VIEWING a specific post on the Community page: reads `action["source_post_id"]`'s `CommunityPost.build` instead — a real `post_id`, zero-hallucination-guarded by `llm/concierge.py` against `community_summary` exactly like `open_community_build`/`load_saved_build`, and resolved by the model via the SAME `current_page`/`viewed_post_id` context those two already use. Unlike `load_saved_build`, a `"community"`-sourced `save_build` does NOT call `state.teardown_builder()`/touch `build_draft`/`page`/`has_unsaved_build_changes` at all — it is a headless clone straight into the user's own drafts/builds, never "let me edit this in the Studio," so the user's own actually-in-progress Studio work, if any, is left completely untouched). It then applies immediately with no separate Python-level confirmation click, and DOES write to the database right away: `destination == "draft"` calls `db.repositories.drafts_repo.save_draft` (the real `draft_builds` table — there is no `saved_builds` table) using the resolved source's components/quantities/mode; `destination == "build"` calls `builds_repo.create_build`, matching `ui/views/create_build.py::_save_actions`'s own real call shape exactly — for `source == "studio"` computing `compatibility_score` via a fresh `evaluate_build` call and reading `synergy_score`/`bottleneck_percentage` from `build_draft_analysis`; for `source == "community"` copying all four scores (plus `total_cost`) straight off the community post's own already-evaluated `Build` row instead, since that build was already scored once when it was first saved — and, on a later `publish_build` turn (reachable only after a `"build"`-destination save), OR immediately in the SAME turn when the save action itself carries `publish_immediately: True` (the fast-track path for "save as X and publish to community", since an LLM-issued `publish_build` normally needs `concierge_last_saved_build` which doesn't exist until AFTER this very save lands) — `builds_repo.set_public` + `community_repo.create_post` (using the save action's own `author_notes` when given). This is judged safe specifically because it's the user's own explicit request acting on their own account's own data, the same trust boundary as them clicking "Save build" themselves. Both `save_build` branches leave `build_draft`/`create_mode`/`page` untouched (a deliberate choice — see the module's own docstring) and use the user's own literal `name` (never an auto-generated one — `_default_saved_build_name()` is now only a last-resort defensive fallback); only the `"build"` branch stores the new build's id/name in `st.session_state["concierge_last_saved_build"]`, the one piece of real state the LLM cannot know on its own and that a later (non-fast-track) `publish_build` action (which carries no build id itself) needs to resolve which build to publish — a `"draft"` save never sets it, since a draft has no publish path.

  **`fix_warnings`/`optimize_bottleneck`** (spec.md §6.7 intents 11/12, this round's addition): `_current_build_context()` now also carries `compatibility_issues` (`engine.compatibility.evaluate_build(build_state, quantities).issues`) and `bottleneck` (`build_draft_analysis`'s own reading when present, else `engine.scoring.live_bottleneck_and_synergy` — the SAME data `create_build.py`'s HUD shows, never a second independently-computed copy; `bottleneck["direction"]` is normalized to `"CPU-bound"|"GPU-bound"|"Balanced"` regardless of which source produced it, since `build_draft_analysis`'s own `limiting_component` uses a different `"CPU"|"GPU"|"None"` vocabulary). `_apply_concierge_action` handles both exactly like `modify_build` (same `state.set_component`/`build_draft_analysis` invalidation/`page = "create_build"` shape, same authoritative real-total return) but NEVER lets the LLM choose the part: `fix_warnings` applies `engine.solvers.resolve_compatibility_issues`'s own deterministic patch; `optimize_bottleneck` applies `llm.advisory.get_build_advisory`'s own already-validated `within_budget.swaps` — root `CLAUDE.md`'s "compatibility is never LLM-gated" rule applies just as much to a Concierge-triggered fix as a manual one. `render_concierge_widget` appends a SECOND authoritative line for these two action types specifically (beyond the existing Total line) — the REAL post-fix warning count or post-rebalance bottleneck reading, freshly recomputed from the now-updated `build_draft`, since the SYSTEM_PROMPT explicitly tells the model never to claim a specific swap happened (it doesn't know which part the deterministic resolver picked).
- `components/auth_modal.py`, `components/build_card.py`, `components/part_picker.py` — reusable widgets shared across views. Both `build_card.py`'s Cost metric and every price `part_picker.py` renders (selected-component captions, candidate-list prices, over-budget deltas) read `st.session_state["selected_currency"]` and format through `ui.format.format_currency` (`spec.md` §7.10) — the underlying `Component.price_usd`/`Build.total_cost` values they read are always real, unconverted USD. `build_card.py`'s `render_build_card(..., confirm_labels=frozenset({"Delete"}))` gates any action named in `confirm_labels` behind a Yes/Cancel step before its callback fires — use this for any future destructive action, not just Delete. `part_picker.py` renders each slot as a status-badged card with a `st.popover` drawer (not `st.expander`) for changing the pick, plus a slot-level `"✕"` clear button (`key=f"clear_{category}"`) next to the popover trigger — not inside the drawer — so a filled slot can be emptied in one click; the drawer itself holds only the candidate list, no bottom "Remove" button. **Industrial empty/filled slot styling** (spec.md §7.4.1, this round's redesign): the slot's own `st.container` carries `key=f"picker_slot_{category}" + ("_filled"|"_empty")` — `theme.inject_css()` targets the `"_empty"` suffix (a key-substring CSS technique) to give an unfilled slot a dashed technical wireframe border instead of the app-wide solid glass-panel look every other bordered container gets; the popover trigger reads `"+ Select {category}"` on an empty slot (`"Change {category}"` once filled — no test asserts on the old `"Choose {category}"` wording, checked before changing it). A filled CPU or Motherboard ALSO shows a `theme.tag("✓ {socket} Matched", "success")` when the paired category (`_SOCKET_MATCH_PAIRS`) is also filled with the same socket — confirming an already-solver-guaranteed fact (every candidate here is pre-filtered compatible by `_candidates_for` in `create_build.py`), not a new check. For `"RAM"`/`"Storage"` specifically, when a component is selected, `render_part_picker`'s optional `quantity`/`on_quantity_change`/`quantities` params add a compact `st.number_input("Qty", ...)` stepper right below the price/specs caption (price caption switches to a `price × qty = total` format once qty > 1) — the stepper's `max_value` comes from `ui.state.resolve_effective_quantity_limit(build_state, category, quantities, budget_ceiling)`, NOT a duplicated/independent calculation. That function returns `(effective_max, reason, limit_kind)`, combining the real physical limit (`engine.compatibility.resolve_quantity_limit` — real per-module RAM math, real `m2_slots` for NVMe Storage) with a budget-affordability limit (only when `budget_ceiling` is not `None`, i.e. Budget mode) and picking whichever is tighter: `limit_kind == "physical"` shows the motherboard-derived caption, `"budget"` shows a distinct budget-ceiling caption (and the widget's `max_value` itself blocks the increment before it happens, not just a post-hoc warning), `"none"` falls back to a UI-only `_FALLBACK_QUANTITY_CAP = 4` — honestly captioned as a generic safety cap, never presented as a motherboard-specific fact (e.g. SATA storage, which has no real port-count data anywhere in this catalog). Before rendering the widget, any stale `st.session_state[f"qty_{category}"]` value exceeding the newly-computed max is clamped down first — a real Streamlit gotcha: a keyed widget ignores its `value=` argument on every rerun after the first and instead uses whatever's already in session state, so if the effective limit shrinks (from either the physical or budget side) without this pre-clamp, `st.number_input` raises a raw `StreamlitAPIException` instead of silently re-clamping. **Fixed** (was tracked as a known gap): `ui.state.set_quantity`/`remove_component` now sync the stepper's own widget key directly (`_sync_qty_widget_key`, `ui/state.py`) whenever the real quantity changes — the SINGLE source of truth for `qty_{category}`'s naming convention now lives in `ui/state.py` itself rather than requiring every out-of-band caller (the AI Concierge's `modify_build` quantity handling, the advisory's stretch-upgrade `set_quantity` action) to know it. The one wrinkle: Streamlit forbids writing to (or popping) a widget's session-state key AFTER that widget has already been instantiated in the CURRENT script run (`StreamlitWidgetAlreadyInstantiatedError`) — this fires for real when `set_quantity` is called from the stepper's OWN on-change callback (the widget already rendered earlier in this same run, using the just-typed value) or from create_build.py code that runs after the part-picker grid. `_sync_qty_widget_key` silently swallows exactly that one exception in exactly that context — harmless, since in the on-change case the write would be redundant anyway (the widget's own interaction already put the same value there), and in the after-the-grid case `build_draft["quantities"]` is already correct and gets picked up on the very next fresh render, before that key's widget has instantiated in that new run. No other category gets this control.

## Allowed imports
- `streamlit`.
- `auth.service`, `auth.session`.
- `engine.*` (compatibility, solvers, scoring) — for computing what to display, never to persist.
- `db.repositories.*` — for reading/writing builds, components, community data.
- `llm.client` — for build analysis display. `analyze_build(...)` never raises (see `llm/CLAUDE.md`), so there is no fallback branch to write here. `response.source` (`"llm"` vs `"heuristic"`) is still on every response, even though the summary banner no longer surfaces it as a badge — a future view is free to read it again.
- `llm.advisory` — for the "✨ Get AI Analysis & Upgrade Path" advisory. `get_build_advisory(...)` also never raises; its `["source"]` key IS surfaced (a `st.caption` inside the advisory expander), unlike `analyze_build`'s badge.
- `llm.concierge` — for the sidebar AI Concierge (`components/chat_assistant.py`). `get_concierge_response(...)` also never raises; its `action` (when present) is applied immediately by the caller with no confirmation step (see `spec.md` §7.8 for why that's safe here).

## Forbidden
- No SQL, no SQLAlchemy imports — go through `db.repositories`.
- No compatibility/scoring math inlined in a view — call `engine/`.
- No direct `httpx`/OpenRouter calls — go through `llm.client`.
- No view may bypass the auth gate in `router.py` by setting `st.session_state["page"]` directly to a gated page without an `auth_user` present.

## State ownership
Own and mutate only the `st.session_state` keys listed in `spec.md` §7.1 (`page`, `auth_user`, `auth_mode`, `auth_error`, `create_mode`, `build_draft`, `build_draft_analysis`, `advisory_cache`, `stretch_applied_keys`, `sort_criteria`, `previous_builds_filter`, `selected_post_id`, `fork_source_build_id`, `concierge_messages`, `has_unsaved_build_changes`, `concierge_last_saved_build`, `pending_community_filters`, `selected_currency`, `pending_currency_switch`, `community_reply_target`), and prefer the helpers in `state.py` over raw dict writes scattered across view files. `community_reply_target` (`int | None`, not in `_DEFAULTS` — only exists once the user has clicked "Reply" at least once this session) is owned entirely by `views/community.py`'s own `_set_reply_target`/`_submit_reply` callbacks — a real `CommunityComment.id` (globally unique, so not scoped per-post) or `None`. `pending_currency_switch` (`str | None`, not in `_DEFAULTS` — an ad-hoc key that only exists once a Concierge `currency_switch` response has actually fired, same "one-shot staging" precedent as `pending_community_filters`) is written only by `components/chat_assistant.py` and consumed (popped, one-shot) only by `app.py`, immediately before its own currency `st.selectbox` instantiates — `chat_assistant.py` cannot write `selected_currency` directly here, since that widget already rendered earlier in the very script pass its handler runs in. `selected_currency` (`spec.md` §7.10) is owned entirely by `app.py`'s sidebar `st.selectbox` — a pure display preference, never written anywhere else. `auth_user`/`auth_mode`/`auth_error` should be mutated only via `auth.session` helpers (`log_in`, `log_out`, `set_auth_mode`), never as raw dict writes. `concierge_last_saved_build` (`{"build_id": int, "name": str} | None`) is owned entirely by `components/chat_assistant.py`: set when a Concierge `save_build` action with `destination == "build"` is applied (never set for `destination == "draft"` — a draft has no publish path), read (never popped — a later `"build"`-destination `save_build` in the same session simply overwrites it) when a later `publish_build` action needs to know which real build to publish. Deliberately a distinctly-named key, not a reuse of the retired `concierge_pending_action` key from an unrelated, now-removed confirm-before-apply mechanism. `pending_community_filters` (`dict | None`, not in `_DEFAULTS` — an ad-hoc key that only exists once a Concierge navigation-with-filters action has actually fired) is written only by `components/chat_assistant.py` (a Concierge `navigate` action's `filters` payload) and consumed (popped, one-shot) only by `views/community.py::_apply_pending_community_filters` — neither module writes to the other's real widget keys (`community_mode_filter`/`community_price_filter`/`community_domain_filter`/`community_tier_filter`) directly, since only `community.py`, at render time, has the live feed data needed to resolve a requested filter into one of those widgets' real options safely.

## LLM debounce/cache contract
`llm.client.analyze_build(...)` already checks `llm_cache` internally before calling OpenRouter — `ui/` doesn't need to compute the cache key itself. What `ui/` *is* responsible for: not calling `analyze_build` on every single part-picker rerun. `create_build.py`'s `_maybe_auto_analyze` is the one deliberate exception to "gate behind an explicit click" — by product decision, it auto-calls `analyze_build` the instant a build first becomes complete (all 8 core categories filled), across every creation mode. This is still bounded, not "every rerun": the trigger condition is `build_draft_analysis is None AND build is complete`, and `ui/state.py`'s `set_component`/`remove_component` only set `build_draft_analysis` to `None` on an actual component change — so a rerun that doesn't change the build (opening a popover, adjusting an unrelated widget) never re-fires it. (The summary banner's old compact "🔮 Analyze" manual-retrigger button was removed in a later round by explicit product decision — there is no manual re-trigger for `analyze_build` anymore, only the automatic one.)

`llm.advisory.get_build_advisory(...)` has NO persistent `llm_cache` entry of its own (a deliberate scope decision — see `llm/CLAUDE.md`) and is never auto-triggered — it stays behind the explicit "✨ Get AI Analysis & Upgrade Path" button (`create_build.py`'s `_advisory_controls`) on every click, since unlike the synergy/bottleneck read it isn't part of "what a complete build inherently has," it's an on-demand deeper analysis. Its ONLY caching layer is `st.session_state["advisory_cache"]`, a plain dict keyed by `(sorted (category, component.id) pairs, mode, current_budget_or_cost)` — computed fresh (not stored in a session-state slot) on every render from the CURRENT build, so a cache hit needs no re-click and a build/mode/cost change simply has no entry yet (no stale display, no manual invalidation needed).

**Any test that drives `create_build.py`/the Concierge widget through `streamlit.testing.v1.AppTest`** must neutralize all three LLM entry points (`analyze_build`, `get_build_advisory`, AND `get_concierge_response`) — e.g. `monkeypatch.delenv("OPENROUTER_API_KEY", raising=False)` AFTER importing `db.database` (its module-level `load_dotenv()` repopulates `os.environ` from a real `.env` at import time, so clearing the var before that import is a no-op — a real bug caught during this feature's own development), ideally as an autouse fixture — otherwise a real `.env` key present in the test process turns nearly every UI smoke test that completes a build into a live, billed OpenRouter call, violating this project's "no live network calls in tests" rule. See `tests/test_ui_smoke.py`'s `_no_live_llm_calls` autouse fixture.
